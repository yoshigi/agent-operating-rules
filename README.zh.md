# Agent Operating Rules（中文版）

**一句話重點**：這個 repo 寫的是一個人怎麼把工作交給 AI Agent、怎麼驗收 Agent 交回來的東西，以及怎麼讓規則不會越積越亂。這套方法是給人用的，不是程式碼。

---

## 先講一個小故事

你請 Agent 取消一個每天早上跑的排程，它回覆完成。你又 request 了兩次，它都回覆完成。但隔天你發現排程依然在跑，表示這裡有個錯誤。

那錯在哪？Agent 沒有說謊。是一個權限設定在背後擋下了修改。「完成」只是表示這個請求在它那邊處理掉了，不代表實際上真的有東西被改掉。

跟 AI Agent 合作，大部分的問題都長這樣：事情看起來做完了，但沒有人去確認。這個 repo 收的，就是我為了「每次都會去確認」而養成的工作習慣。

## 把這個 repo 想成新人交接筆記

如果明天有一位新同事加入，開始把工作交給 AI Agent，你第一天會跟他交代什麼？會是這三件事：

1. **什麼時候該交出去、交給誰**：不是每件事都該交給 Agent，也不是每件工作都需要最貴的模型。
2. **交回來之後怎麼驗收**：畫面上說完成，不代表事情真的辦好了。
3. **學到新東西時，規則怎麼改**：沒有收納的方法，規則會越積越多，最後沒有人會去讀。

這裡的檔案就是在回答這三題，一個檔案負責一題。

## 誰適合讀

- **你每天都在用 AI Agent**，想少遇到幾次「它說完成，其實沒有」。
- **你正在帶團隊導入 AI**，需要一套大家共用的判斷：哪些事可以交給 Agent、做完怎麼簽收。
- **你在教別人或協助別人導入 AI**，想要真實發生過的錯誤案例，以及事後改了什麼。

這些內容都不需要會寫程式。

## 裡面有什麼

| `delegation.md` | 交辦工作時，到底要寫些什麼？五種可以直接套用的範本，以及讓交辦失敗的常見錯誤。 |

### 關於「模型分級」：交辦前先選對的人

同一家 AI 公司通常會推出好幾個模型，有的快又便宜，有的慢、比較貴，但想得比較深。模型分級，就是交辦工作前，先決定這件事要交給哪一種模型。

可以把它想成公司裡的分工。簡單的核對交給新人，大部分的日常工作交給熟手，困難的判斷才請資深顧問。資深顧問的時薪最高，請他來核對格式就是浪費；反過來，把要緊的決定丟給新人，錯了你也不會馬上發現。

規則檔用三個等級來講這件事，從不點名廠商，因為模型一直在換。你自己對應到手上在用的模型：

| 等級 | 像公司裡的 | 適合交給它的事 |
|------|-----------|----------------|
| **機械級** | 新人 | 檢查格式、比對清單、把已經定好的做法大量套用 |
| **標準級** | 熟手 | 大部分的工作：實作、整理資料、查資料、一般審查 |
| **高判斷級** | 資深顧問 | 困難的除錯、第二意見、風險高的決定 |

**一個例子：Claude 的四個模型，官方定位和我的實際用法**（模型一換就會過時，只是幫你起頭）

| 等級 | 模型 | 官方的說明 | 我的實際用法 |
|------|------|----------------|--------------|
| **機械級** | Claude Haiku 5.5 | 適合量大、要求速度的工作，例如分類、擷取資料、分流；四個裡最快、最便宜 | 目前很少用到 |
| **標準級** | Claude Sonnet 5.5 | 速度和智慧的最佳組合；速度快 | 被派出去做事的 Agent：查資料、寫初稿，以及一般稿件的獨立驗收（這份 README 的審查就是它做的；風險高的審查改請高判斷級） |
| **標準級** | Claude Opus 5.5 | 適合長時間的 Agent 寫程式和知識工作；官方建議，不確定用哪個時，大多數工作先從它開始；速度中等 | 我直接對話、下指令的那條主線：拆解工作、決定交給誰、判斷結果能不能用 |
| **高判斷級** | Claude Fable 5.1 | 適合吃重的推理和長時程的 Agent 工作，或是用你自己的測試，Opus 5.5 調高思考強度後仍不夠的時候；四個裡最慢、最貴 | 前一陣子，我的主線用的就是它；後來主線改成 Opus 5.5 |

官方說「大多數工作先從 Opus 5.5 開始」，講的是選哪個模型；規則檔說「標準級是預設」，講的是交辦時先選的等級。兩者剛好都落在標準級，但說的是兩件事。

**先從 Opus 5.5 開始**：官方建議不確定時先從 Opus 5.5 開始，不夠再換 Fable 5.1，我也建議這樣做。最強的模型用量很大，而大多數人的訂閱方案用量額度有限，一開始就把 Fable 5.1 當預設，額度很快就會用完；拿它做簡單的庶務，就像請資深顧問幫你整理信件。日常交辦照規則檔的做法，先從標準級開始，做不好再升級，把最強的模型留給真正困難、風險最高的判斷。

你用 ChatGPT 或其他廠商的模型，也是一樣的分法：先看那家有哪幾個模型，再照「快又便宜」到「慢但想得深」排進這三級。

**Claude Code 和 ChatGPT 是工具，等級是工具裡選的模型**：ChatGPT 最常見的用法，是在網頁或 App 裡對話；Claude Code 是在你自己的電腦上工作，可以直接讀寫檔案，也能把工作派給其他 Agent。不管用哪個工具，交辦前都可以先選等級。

模型怎麼換，這條都不會變：**每次交辦，都要刻意選等級。** 讓它自動沿用，結果就是貴的模型在做小事、便宜的模型在做要緊的事，而你幾週後才發現。

## 怎麼用（請先嘗試一次看看，再生出適合你的版本）

把這一節當成工作流程的起手式。先用一個框架理解這套方法，再照步驟做一次小實驗。你不需要先判斷這些規則對不對，只要先提出假設、動手驗證、留下真的有效的做法。只要開始嘗試，你就會一步步累積出自己的版本。

### 一個框架：把每條規則當成實驗

每條規則都走同一個循環，三個動作：

1. **建立假設**：先說出你想驗證的事。例如：「交辦時多寫一句驗收標準，Agent 說完成、其實沒完成的次數會變少。」
2. **驗證論述**：照著做一陣子，記下實際發生了什麼，包括沒效的時候。
3. **求證真實方案**：結果支持假設，就留下來變成你的做法；結果不支持，就改寫假設或整條丟掉。

這個 repo 裡的規則，是我用這個循環一條一條留下來的，其中有些已經改過或刪掉。它們對我有效過，但在你的工作裡還只是假設，要等你的結果來驗證。

### 步驟指引：每一步附上原因

1. **先不設規則做一陣子，看事情在哪裡出錯。**

   原因：沒有出錯記錄就寫的規則，只是猜測。我現在每次踩坑，先記下發生了什麼、我原本以為會怎樣，之後才決定要不要改規則。
2. **找出出錯之前就已經出現的訊號。**

   原因：規則要在出錯前提醒你，才有用。我回頭看記錄時，找的是「當時哪裡已經不對勁」，例如 Agent 回報完成，卻沒附任何證據。
3. **把規則寫成「看到這個訊號，我就做這件事」，附一個適用的例子、一個不適用的例子。**

   原因：只寫「要做什麼」的規則，執行的人只能用猜的。附上兩個例子，Agent 和人都知道邊界在哪。
4. **門檻（開始需要規則的分界點）設在你自己的證據指向的地方。**

   原因：這個 repo 裡的數字，像「三個檔案」「三十行」，都是從我的工作量跑出來的。它們證明了這裡有一個值得找的門檻，你的門檻要從你的結果裡找。
5. **同一類錯誤發生第二次，才把筆記升格成規則。**

   原因：每次出錯都加規則，規則增加的速度會快過任何人讀完的速度。發生一次先記筆記，重複發生才立規則。

### 我現在固定的五個做法

這五個是我自己目前實際的工作流程，每個都附上我這樣做的原因；下面「帶得走的五件事」則是可以帶走的原則。你可以挑一個，當成你的第一個實驗。

- **先定好原始來源**：事實一律以原始檔案為準，AI 整理出來的內容只當參考。原因：AI 會很有自信地寫錯。我遇過 AI 在自己的驗收紀錄裡寫「原始資料查不到」，回頭查原始檔，其實兩段內容都在。
- **改之前先備份**：動到重要檔案前，先留一份原檔。原因：改完可以逐字比對，確認不該動的地方真的沒動。
- **做事和驗收分開**：寫完的東西，交給另一個沒看過製作過程的 Agent，照一份清單逐條判過或不過，沒過就改，改完再驗。原因：做的人最容易看不見自己的錯。這份 README 就是照這個流程，審查通過才定稿。
- **收工寫交接筆記**：每次結束前，記下決定了什麼、做到哪裡、下一步是什麼。原因：下次開始時，從筆記接著做，不用重講背景，也留下誰在什麼時候決定了什麼。
- **我的觀點我自己寫**：AI 幫我整理資料，但心得和判斷的欄位留空給我自己寫。原因：判斷是我要負責的部分，交給 AI 寫，就分不清哪些是我真的相信的。

### 今天就能做的第一個動作

挑一件這週要交給 Agent 的事。交辦時多寫一句：「做完後，請告訴我用什麼證據可以確認真的完成了。」然後記下 Agent 給的證據，以及你自己查的結果對不對得上。

一週後回頭看：這一句話，有沒有讓你少遇到一次「它說完成，其實沒有」？有，你就有了第一條自己的規則；沒有，你也多了一筆記錄，知道下一個假設要往哪裡改。

### 擔心的時候

- **「我不會寫程式」**：這裡每一步都是工作習慣，寫一句話、記一筆記錄就能開始。
- **「怕一開始就把規則設錯」**：先在你自己的沙盒（一個不影響正式工作的練習環境）裡試。規則錯了就改或刪，這本來就是實驗的一部分。
- **「不確定這些規則對不對」**：先把它們當成假設，你的實驗結果會給你答案。
- **「怕花太多時間」**：從一件事、一句驗收標準開始。一週只要回頭看一次。

## 帶得走的五件事（五個優先嘗試步驟）

可以先從這五件開始試：

- **指揮的人專心做決定**：你跟 Agent 對話、下指令的那條主線，只留給做決定；細節交給被派出去的 Agent 處理。
- **驗收交給沒參與製作的人**：驗收交給一個沒看過製作過程的人，或另一個 Agent。
- **寫進其他系統的成功，要另外查一次**：任何寫進其他系統的東西，事後都要另外查一次。
- **第二次才立規則**：發生一次，記一條筆記；重複發生，才變成規則。不然規則增加的速度，會快過任何人讀完的速度。
- **規則寫清楚做什麼、為什麼、哪裡不適用**：好執行的規則，要寫做什麼、為什麼，再加一個不適用的例子。

你會發現這五件事都沒有數字。這就是「可以借走的」和「要自己找的」之間，真正的分界線。

## 新手指引（範圍＆使用建議）

- **讀完就能用**：沒有東西要安裝，讀完就是全部的設定，剩下的發生在你的工作習慣裡。
- **當成一個人試過有效的做法**：沒有跟對照組（拿來比較的另一組）比過。把每條規則當成「對一個人有效過一次」的做法。
- **工具改了，規則跟著改**：大約一半的規則，是因為某個工具當時的行為才存在。工具改了，規則就該刪。
- **規則停下的地方，交給你判斷**：模糊的需求、品味問題，刻意留給人判斷。規則沒有反應的時候，就是輪到你自己判斷的時候。

## 這個 repo 的內容怎麼產生（資料治理方法）

這個 repo 的每條規則，都來自我私人工作筆記裡真實發生過的事。從私人筆記到公開版本，中間要走過下面六步。這套流程本身，就是上面「驗收交給沒參與製作的人」「寫進其他系統的成功，要另外查一次」這兩條的應用。

1. **找到原始事件**：每條規則都要對得上一次真實發生的錯誤，以及事後改了什麼。對不上真實事件的規則不收。
2. **去識別化**：名字、公司、路徑、日期、廠商和確切數字都拿掉，只留大約的量級，例如「幾十行」，不留確切數字。公開前用搜尋逐項檢查，命中數是零才算過。唯一的例外是「模型分級」一節中的廠商與模型舉例，那是刻意放上去幫你起頭的，規則檔本身仍然不點名廠商。
3. **抽象化檢查**：例子抽象到可以公開之後，每個元素還要一一對得回原本的事件；比喻也一樣，多出原事件沒有的情節就刪掉。例子一抽象就失去意義的，整條規則不放，因為沒有例子的規則只是口號。
4. **獨立驗收**：稿子交給一個沒參與撰寫的審查者（另一個 Agent），照一份清單逐條判過或不過，例如事實有沒有出處、數字對不對得上檔案、有沒有留下可識別的資訊。沒過就改，改完再驗。審查紀錄留在私人筆記，不公開。
5. **作者簽核**：發布前由我本人看過、同意放行，AI 不自行發布。
6. **留下紀錄**：公開 repo 每次修改的內容和原因，都留在 git 的版本修改紀錄裡，任何人都可以回頭查；私人筆記裡的原始紀錄不公開。

這套流程讓這個 repo 能老實告訴你，哪些東西無法推廣到你的環境。這個 repo 裡值得相信的是推理過程，不是數字。

## 讀完後，帶走一個校正問題

你要校正的地方是：上一次 Agent 跟你說完成時，你是怎麼確認它真的完成了？
