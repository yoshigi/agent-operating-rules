# Agent Operating Rules（中文版）

**一句話重點**：一個人怎麼把工作交給 AI Agent、怎麼驗收交回來的東西，以及怎麼讓規則不會越積越亂。這是給人用的方法，不是程式碼。

> **想帶團隊或公司導入 AI？** 先看 [AI 導入工作框架](framework/framework.zh.md)：從「先挑對的事」到五個步驟、三個導入階梯，以及第一週可以怎麼開始。本頁和五份規則檔是它背後的操作細節。

---

## 先講一個小故事

你請 Agent 取消一個每天早上跑的排程，它回覆完成。你又 request 了兩次，它都回覆完成。但隔天你發現排程依然在跑，表示這裡有個錯誤。

錯在哪？Agent 沒有說謊，是一個權限設定在背後擋下了修改。「完成」只表示請求在它那邊處理掉了，不代表東西真的被改掉。

跟 Agent 合作，大部分問題都長這樣：看起來做完了，但沒有人去確認。這個 repo 收的，就是我為了「每次都去確認」養成的工作習慣。

## 把這個 repo 想成新人交接筆記

新同事明天開始把工作交給 Agent，你第一天會交代三件事：

1. **什麼該交出去、交給誰**：不是每件事都該交，也不是每件事都需要最貴的模型。
2. **交回來怎麼驗收**：畫面說完成，不代表真的辦好了。
3. **規則怎麼改**：沒有收納的方法，規則越積越多，最後沒人讀。

一個檔案回答一題。

## 誰適合讀

- **每天用 AI Agent 的人**，想少遇到幾次「它說完成，其實沒有」。
- **帶團隊導入 AI 的人**，需要共用的判斷：哪些事可以交、做完怎麼簽收。
- **教別人導入 AI 的人**，想要真實的錯誤案例，以及事後改了什麼。

都不需要會寫程式。

### 關於「模型分級」：交辦前先選對的人

同一家公司通常有好幾個模型，有的快又便宜，有的慢、貴，但想得深。模型分級，就是交辦前先決定交給哪一種。

像公司分工：簡單核對給新人，日常工作給熟手，困難判斷才請資深顧問。請顧問核對格式是浪費；把要緊的決定丟給新人，錯了你也不會馬上發現。

規則檔用三個等級，不點名廠商，因為模型一直在換：

| 等級 | 像公司裡的 | 適合交給它的事 |
|------|-----------|----------------|
| **機械級** | 新人 | 檢查格式、比對清單、大量套用定好的做法 |
| **標準級** | 熟手 | 大部分工作：實作、整理資料、查資料、一般審查 |
| **高判斷級** | 資深顧問 | 困難的除錯、第二意見、風險高的決定 |

**例子：Claude 的四個模型**（模型一換就會過時，只是幫你起頭）

| 等級 | 模型 | 官方的說明 | 我的實際用法 |
|------|------|----------------|--------------|
| **機械級** | Claude Haiku 5.5 | 適合量大、要求速度的工作，例如分類、擷取資料、分流；四個裡最快、最便宜 | 目前很少用到 |
| **標準級** | Claude Sonnet 5.5 | 速度和智慧的最佳組合；速度快 | 派出去做事的 Agent：查資料、寫初稿、一般稿件的獨立驗收 |
| **標準級** | Claude Opus 5.5 | 適合長時間的 Agent 寫程式和知識工作；官方建議，不確定用哪個時，大多數工作先從它開始；速度中等 | 我直接下指令的主線：拆解工作、決定交給誰、判斷結果能不能用 |
| **高判斷級** | Claude Fable 5.1 | 適合吃重的推理和長時程的 Agent 工作，或是用你自己的測試，Opus 5.5 調高思考強度後仍不夠的時候；四個裡最慢、最貴 | 之前主線用它，後來改成 Opus 5.5 |

**先從 Opus 5.5 開始**：官方建議不確定時先用 Opus 5.5，不夠再換 Fable 5.1，我也這樣建議。最強的模型用量大，訂閱額度很快就會用完；拿它做庶務，就像請資深顧問整理信件。把它留給真正困難、風險最高的判斷。

用 ChatGPT 或其他廠商也一樣：把那家的模型從「快又便宜」到「慢但想得深」排進這三級。工具（ChatGPT、Claude Code）不等於等級，等級是你在工具裡選的模型。

不管模型怎麼換：**每次交辦，都刻意選等級。** 讓它自動沿用，就會變成貴的模型做小事、便宜的模型做要緊的事，而你幾週後才發現。

## 怎麼用（請先嘗試一次看看，再生出適合你的版本）

這一節是起手式：先理解一個框架，再照步驟做一次小實驗。把規則當成待驗證的假設：提出假設、動手驗證、留下有效的做法。

### 一個框架：把每條規則當成實驗

1. **建立假設**：例如「交辦時多寫一句驗收標準，說完成其實沒完成的次數會變少」。
2. **驗證論述**：照做一陣子，記下實際發生的事，包括沒效的時候。
3. **求證真實方案**：結果支持就留下；不支持就改寫或丟掉。

這裡的規則是我用這個循環留下來的，有些已經改過或刪掉。在你的工作裡，它們還只是假設。

### 步驟指引：每一步附上原因

1. **先不設規則做一陣子，看事情在哪裡出錯。** 沒有出錯記錄就寫的規則，只是猜測。我現在每次踩坑，先記下發生什麼、原本以為會怎樣，之後才決定要不要改規則。
2. **找出出錯前就出現的訊號。** 規則要在出錯前提醒你才有用。我回頭看記錄時，找的是「當時哪裡已經不對勁」，例如 Agent 回報完成，卻沒附證據。
3. **把規則寫成「看到這個訊號，就做這件事」，附一個適用、一個不適用的例子。** 有了邊界，Agent 和人都不用猜。
4. **門檻（開始需要規則的分界點）從你自己的證據找。** 這裡的「三個檔案」「三十行」是我的工作量跑出來的，你的要從你的結果找。
5. **同一類錯誤第二次發生，才升格成規則。** 每次出錯都加規則，規則會多到沒人讀得完。

### 我現在固定的五個做法

我目前實際的工作流程，各附原因。挑一個當你的第一個實驗。

- **先定好原始來源**：事實以原始檔案為準，AI 的整理只當參考。原因：AI 會很有自信地寫錯，我遇過它說「原始資料查不到」，其實內容都在。
- **改之前先備份**：原因：改完可以逐字比對，確認不該動的沒動。
- **做事和驗收分開**：寫完交給沒看過過程的 Agent，照清單判過或不過，沒過就改再驗。原因：做的人最看不見自己的錯。這份 README 就是這樣定稿的。
- **收工寫交接筆記**：記下決定了什麼、做到哪、下一步。原因：下次直接接著做，也留下誰在何時決定了什麼。
- **我的觀點我自己寫**：AI 整理資料，心得和判斷留給我寫。原因：判斷是我要負責的，交給 AI 就分不清哪些是我真的相信的。

### 今天就能做的第一個動作

挑一件這週要交給 Agent 的事，交辦時多寫一句：「做完後，請告訴我用什麼證據可以確認真的完成了。」記下它給的證據，和你自己查的結果對不對得上。

一週後回頭看：有沒有少遇到一次「它說完成，其實沒有」？有，你就有了第一條規則；沒有，你也知道下一個假設要往哪改。

### 擔心的時候

- **「我不會寫程式」**：每一步都是工作習慣，寫一句話就能開始。
- **「怕把規則設錯」**：先在不影響正式工作的練習環境試，錯了就改或刪。
- **「不確定規則對不對」**：當成假設，讓結果回答。
- **「怕花太多時間」**：一件事、一句驗收標準，一週回頭看一次。

## 帶得走的五件事（五個優先嘗試步驟）

- **指揮的人專心做決定**：主線只留給做決定，細節交給派出去的 Agent。
- **驗收交給沒參與製作的人**：一個沒看過過程的人，或另一個 Agent。
- **寫進其他系統的成功，要另外查一次**：Agent 改了排程、檔案或設定，就自己打開看一次。
- **第二次才立規則**：一次記筆記，重複才變規則。
- **規則寫清楚做什麼、為什麼、哪裡不適用**。

這五件都沒有數字。這就是「可以借走的」和「要自己找的」之間的分界線。

## 新手指引（範圍＆使用建議）

- **讀完就能用**：沒有東西要安裝，剩下的發生在你的工作習慣裡。
- **當成一個人試過有效的做法**：沒有跟對照組（拿來比較的另一組）比過。
- **工具改了，規則跟著改**：大約一半的規則因某個工具當時的行為而存在，工具改了就該刪。
- **規則停下的地方，交給你判斷**：模糊的需求、品味問題，刻意留給人。

## 這個 repo 的內容怎麼產生（資料治理方法）

每條規則都來自我私人筆記裡真實發生過的事。公開前要走六步，這本身就是「驗收交給沒參與製作的人」「寫進其他系統的成功，要另外查一次」的應用。

1. **找到原始事件**：對不上真實錯誤與事後改動的規則不收。
2. **去識別化**：名字、公司、路徑、日期、廠商和確切數字都拿掉，只留量級；公開前逐項搜尋，命中為零才算過。例外是「模型分級」的廠商舉例，刻意放上來幫你起頭。
3. **抽象化檢查**：抽象後的例子和比喻，每個元素都要對得回原事件；一抽象就失去意義的規則不放。
4. **獨立驗收**：交給沒參與撰寫的 Agent 照清單逐條判，例如事實有沒有出處、有沒有可識別資訊；沒過就改再驗。
5. **作者簽核**：我本人看過才放行，AI 不自行發布。
6. **留下紀錄**：每次修改的內容和原因都在 git 的版本修改紀錄裡，任何人都能查。

所以這個 repo 能老實告訴你，哪些東西推廣不到你的環境。值得相信的是推理過程，不是數字。

## 讀完後，帶走一個校正問題

回到開頭的排程：Agent 回了三次「完成」，排程還在跑。關鍵是你拿什麼當作「完成」的證據。通常是這三種之一：

- **相信它的回覆**：確認到的是「它有回應」。
- **看它給的報告**：多了一層，但報告還是它自己寫的，它可能真心以為做完了。
- **自己到目的地查**：打開排程清單或那個檔案，親眼看到改了。只有這種確認到結果本身。

落在前兩種，就是你可以開始實驗的地方。

你要校正的地方是：上一次 Agent 跟你說完成時，你是怎麼確認它真的完成了？
